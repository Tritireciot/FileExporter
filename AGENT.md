# Порядок работы с FileExporter / PrintServer

Этот файл описывает текущий рабочий процесс для агентов. Код важнее документации: если `README.md` или `NewsPrint.yaml` расходятся с реализацией, проверьте код и тесты, затем приведите документацию в соответствие с согласованным поведением.

## 1. Ориентация перед изменениями

1. Проверьте `git status --short`: в рабочей копии могут быть незавершённые правки пользователя. Не перезаписывайте и не откатывайте их.
2. Определите узкую область задачи через `rg --files` и `rg -n`. Читайте связанные файлы, а не весь репозиторий.
3. Проследите путь данных и ошибок от входа до результата. Для PrintServer это обычно `server/app.go` → `handlers` → `transformer` → `compiler` / `cache` / `diagnostic`.
4. Перед правкой установите ожидаемое поведение по коду, существующим тестам и уточнениям пользователя. `NewsPrint.yaml` описывает HTTP API, но может отставать от кода.

## 2. Карта PrintServer

| Область | Где искать |
| --- | --- |
| Маршруты и авторизация | `PrintServer/server` |
| JSON-запросы, ответы и HTTP-ошибки | `PrintServer/handlers` |
| Сценарии render / preview / validate, запросы к другим сервисам | `PrintServer/transformer` |
| Разбор DSL и диагностические позиции | `PrintServer/compiler`, `PrintServer/diagnostic` |
| Скомпилированные шаблоны и LRU | `PrintServer/cache` |
| Контракт HTTP | `NewsPrint.yaml` |
| Тесты этих областей | `tests/handlers_test`, `tests/transformer_test`, `tests/compiler_test`, `tests/cache_test` |

`PrintServer/docxgo` — отдельный вложенный Go-модуль. Заходите в него только для задач по DOCX. PDF сейчас не опубликован в HTTP API. Запрос `/printcontent` идёт к источнику рабочих данных, а запросы `/published` и `/preview-data` — к ConfigAppServer; не смешивайте их ошибки.

## 3. Изменение и проверка

1. Если меняется поведение, добавьте или измените небольшой тест в соответствующем пакете `tests`. Для HTTP проверяйте роутер, статус и формат ответа; для transformer — взаимодействие с upstream и кэшем; для compiler — результат и диагностический код/позицию.
2. Внесите минимальную правку в код и выполните `gofmt` для изменённых Go-файлов.
3. Сначала запустите затронутый пакет тестов, затем один полный прогон `./tests/...`. Повторяйте полный прогон только при конкретном риске или после новых правок. Не запускайте `go test ./...` без причины: это выходит за согласованную область тестов.
4. Проверьте `git diff --check` и `git diff` по затронутым файлам. Если поменялся HTTP-контракт, сверьте `NewsPrint.yaml` с кодом и тестами.
5. В ответе кратко укажите, что изменено, какие тесты выполнены и что осталось непроверенным или падает. Не исправляйте посторонние правки пользователя ради зелёного результата.

## 4. Тесты: предпочтительно Docker

Тестовый образ задан в `Dockerfile.test`, сервис — в `docker-compose.test.yml`. Образ запускает `go test -v ./tests/... -count=1 -race -timeout=120s`; в Alpine установлен `build-base` для race detector. Запускайте тесты через Docker: локальный Windows-запуск с `-race` может завершиться ошибкой доступа к временным `.exe`.

После изменений исходников пересоберите образ, поскольку Dockerfile копирует код внутрь него:

```sh
docker compose -f docker-compose.test.yml build test-backend
```

Точечный прогон (замените пакет на нужный):

```sh
docker compose -f docker-compose.test.yml run --rm --no-deps test-backend go test -v ./tests/compiler_test -count=1 -race -timeout=120s
```

Полный прогон использует `CMD` из `Dockerfile.test`:

```sh
docker compose -f docker-compose.test.yml run --rm --no-deps test-backend
```

Перед Docker-запуском нужен `.env` из `example.env`, так как он указан в compose. `run` используется для одноразового запуска тестов; у сервиса в compose сейчас задано `restart: always`. При добавлении новых пакетов держите их внутри `tests`, чтобы их включал полный прогон.

## 5. Инварианты, которые легко нарушить

- В `validate-template` обязательны `template_id`, `content_hash` и объект `data`. Хеш — SHA-256 точных байтов `template`; проверяйте его до использования кэша.
- Успешная валидация может положить скомпилированный шаблон в основной кэш. Не сохраняйте невалидные результаты и не подменяйте опубликованную ревизию записью с другим хешем.
- Публичные маршруты сейчас проходят JWT middleware; внутренний `validate-template` дополнительно требует `SubToken`. Тесты handlers создают тестовый RSA-ключ и JWT в `TestMain`.
- Ошибки DSL возвращают конкретные коды из `PrintServer/diagnostic/code.go`; позиции, если есть, относятся к исходному шаблону. При работе с символом `#` учитывайте экранирование обратной косой чертой.
